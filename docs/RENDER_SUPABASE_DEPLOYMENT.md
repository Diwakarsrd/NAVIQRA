# NAVIQRA v0.5.0 — Render + Supabase deployment runbook

This is a deployment configuration for a **controlled production pilot**. It does not
certify the service for high-risk traveler data, payments, ticketing, or live bookings.

## Architecture

- Render Docker Web Service: `naviqra-api`, Singapore region, 1 CPU / 2 GB baseline.
- Supabase PostgreSQL: external managed database; use the **Session Pooler** connection
  string (port 5432) for a Render workload. Enforce TLS. Prefer `sslmode=verify-full`
  with the Supabase CA certificate mounted as a Render secret file; `sslmode=require`
  encrypts traffic but does not verify the server certificate. Do not use the Supabase
  `service_role` API key as a database password.
- Render terminates public TLS. The API is exposed through Render's HTTPS hostname.
- `render.yaml` uses Docker `dockerCommand`, sets `autoDeployTrigger: off`, and uses a 1 CPU / 2 GB instance so a push cannot silently deploy a new release.

## 1. Create Supabase project and prepare database

1. Create a Supabase project in a region close to the Render Singapore service, subject
   to your latency and data-residency requirements.
2. In Supabase **Connect**, select **Session Pooler** and copy the URI. The username
   typically includes the project reference, e.g. `postgres.<PROJECT_REF>`.
3. In Supabase SQL Editor, run `migrations/0001_postgres_foundation.sql` as the project
   database owner. Confirm all tables and indexes exist.
4. Edit `migrations/SUPABASE_RUNTIME_ROLE.sql`: replace the example password with a
   unique randomly generated password. Run it as the project owner.
5. Construct a second Session Pooler URI using username
   `naviqra_runtime.<PROJECT_REF>` and that password (shared-pooler usernames include
   the project reference). URL-encode reserved characters in the password. Add `?sslmode=verify-full&sslrootcert=/etc/secrets/supabase-prod-ca.crt`. In Render, add the Supabase root CA certificate as a secret file at that path. If certificate verification is not yet configured, use `sslmode=require` only as a temporary encrypted-transport baseline and record the exception.
6. Store the owner/migration URI separately. Never configure it as the Render runtime
   `NAVIQRA_DATABASE_URL`. In Render, add the Supabase root CA certificate as a secret
   file (for example `/etc/secrets/supabase-prod-ca.crt`) and append
   `sslmode=verify-full&sslrootcert=/etc/secrets/supabase-prod-ca.crt` to the runtime URI.
   If certificate verification is not yet configured, use `sslmode=require` only as a
   temporary encrypted-transport baseline and record the exception.
7. Confirm runtime role can `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on required tables,
   but cannot `CREATE` tables or alter schema.

The runtime application currently uses application-level tenant predicates and
credential checks. The SQL migration does **not** enable PostgreSQL row-level security.
Do not expose the database directly to end users or untrusted clients.

## 2. Generate tenant credentials

Run locally for each tenant:

```bash
python scripts/generate_tenant_key.py demo
```

Keep `CLIENT_TENANT_KEY` in a trusted server-side client secret store. Put only the
`SERVER_TENANT_KEY_HASHES` JSON into Render's `NAVIQRA_TENANT_KEY_HASHES`. Never place
tenant keys in Expo `EXPO_PUBLIC_*`, browser JavaScript, source control, or logs.

Render Blueprint generates `NAVIQRA_API_KEY`; keep it private. Render generates a 256-bit value for this variable, satisfying the application minimum. Render generates a

## 3. Deploy on Render

1. Push the release repository to a GitHub repository you control.
2. In Render, choose **New + → Blueprint**, connect that repository, and select
   `render.yaml`.
3. Review the service. `naviqra-api` uses Docker, Singapore, 1 CPU / 2 GB, health check
   `/health`, and manual deploys (`autoDeployTrigger: off`).
4. Set the following secret/environment values in Render:
   - `NAVIQRA_DATABASE_URL`: runtime-role Supabase Session Pooler URI.
   - `NAVIQRA_TENANT_KEY_HASHES`: generated JSON map.
   - `NAVIQRA_ALLOWED_HOSTS`: `naviqra-api.onrender.com` plus any custom API domain.
   - `NAVIQRA_CORS_ORIGINS`: exact HTTPS browser origins, comma-separated. If no browser
     frontend calls the API, set an empty value and omit browser CORS entirely.
5. Confirm `NAVIQRA_API_KEY` is generated by Render and not shared.
6. Deploy manually. Wait for Render build and `/health` health check to pass.
7. If using a custom domain, add it in Render, configure DNS, wait for TLS provisioning,
   then add the exact hostname to `NAVIQRA_ALLOWED_HOSTS` and deploy again.

Do not set `NAVIQRA_DB_AUTO_CREATE=true`. Do not use `*` for CORS or allowed hosts.

## 4. Verify deployment

Set `BASE_URL` and use a tenant key generated for a test tenant:

```bash
export BASE_URL=https://naviqra-api.onrender.com
curl -fsS "$BASE_URL/health"
curl -i "$BASE_URL/v1/platform/capabilities"  # expected 404 in production
curl -i "$BASE_URL/v2/tenants/demo/capabilities" # expected 401 without tenant headers
curl -fsS -H "X-Tenant-ID: demo" -H "X-Tenant-Key: $CLIENT_TENANT_KEY" \
  "$BASE_URL/v2/tenants/demo/capabilities"
```

Then execute the complete smoke checklist in `docs/PRODUCTION_VERIFICATION_CHECKLIST.md`.
Do not send real traveler data during initial verification.

## 5. Operations

- Configure Render alerting/notifications for deploy failures and service health.
- Configure Supabase backup/PITR appropriate to the chosen plan and verify a restore
  into a separate project before accepting real customer data.
- Monitor Supabase connection usage and Render memory/CPU. The current adapter opens
  short-lived database connections; load test concurrency before scaling workers.
- Keep `autoDeployTrigger: off`; review CI and deploy manually after passing checks.
- Rotate tenant keys by temporarily accepting old + new hashes, update clients, then
  remove old hashes. Rotate DB password and Render secrets through a controlled deploy.
- Establish retention/deletion procedures, incident response, on-call ownership,
  log redaction, and a privacy/legal review before production customer onboarding.

## Rollback

Keep the previous Render deploy available. If health or smoke tests fail, roll back to
that deploy. Database migrations are additive in this release; never roll back by
restoring an old application against an incompatible schema without testing. Restore
from a verified Supabase backup only under an incident runbook.

## Known release limits

- No OIDC/SSO or built-in role/permission system.
- No PostgreSQL RLS; tenant isolation is application-enforced.
- No shared distributed rate limiter/WAF configuration included in this blueprint.
- No independent penetration test or formal SLO validation.
- No live airline/hotel supplier inventory, payment, ticketing, or booking integration.
- Synthetic providers are non-bookable; all purchase/booking operations remain gated.

### Automated read-only smoke test

After setting the environment variables, run:

```bash
export NAVIQRA_BASE_URL=https://naviqra-api.onrender.com
export NAVIQRA_TEST_TENANT_ID=demo
export NAVIQRA_TEST_TENANT_KEY='<raw key generated locally>'
python scripts/verify_deployment.py
```

This checks health, disabled legacy/docs routes, missing-credential rejection,
valid tenant authentication, and `no-store` cache headers. It does not test cross-tenant
isolation, backup restore, rate limits, or production load; those require separate tests.
